# مدل امنیتی

این سند صادقانه توضیح می‌دهد چه چیزی محافظت می‌شود، چه چیزی نمی‌شود، و چرا
این معماری برای یک فروشگاه کوچک انتخاب درستی است.

---

## خلاصه در یک پاراگراف

توکن گیت‌هاب هرگز در متن ساده نوشته نمی‌شود. مدیر یک رمز انتخاب می‌کند؛ مرورگر با
PBKDF2-SHA256 (۳۰۰٬۰۰۰ دور) و یک salt تصادفی از آن کلید می‌سازد و توکن را با
AES-256-GCM رمز می‌کند. فقط ciphertext در `data/vault.json` می‌ماند. هنگام ورود،
همان رمز، همان کلید را می‌سازد و توکن فقط در حافظه‌ی همان تب رمزگشایی می‌شود.

```
رمز عبور ──PBKDF2(300k, salt)──► کلید ۲۵۶ بیتی ──AES-GCM(iv)──► token
                                    ▲
                                    └── هیچ‌جا ذخیره نمی‌شود
```

## آیا `.gitignore` می‌تواند «جفت رمز و توکن» را مخفی کند؟

**نه — و این نکته مهم است.**

دو مفهوم را باید جدا کرد:

| مفهوم | کارکرد |
| --- | --- |
| `.gitignore` | جلوی **کامیت شدن** فایل‌های محلی را می‌گیرد. برای فایل‌های حساسی مثل `local.secret.json` خوب است. |
| رمزنگاری | حتی اگر فایل کامیت و منتشر شود، **بدون رمز بی‌فایده** است. |

در یک مخزن عمومی، هر چیزی که کامیت شود عمومی است؛ و اگر فایلی یک‌بار کامیت شده باشد،
بعد از `.gitignore` کردن هم در تاریخچه باقی می‌ماند. بنابراین ساختار درست این است:

1. هرگز توکن خام را در فایل قرار نده (نه در `.env`، نه در JS).
2. فقط نسخه رمزگذاری‌شده را کامیت کن.
3. فایل‌های موقت و ابزارهای محلی را در `.gitignore` بگذار.

در این پروژه، `.gitignore` این موارد را کنار می‌گذارد:

```
.env
secrets/
*.secret.json
data/local.secret.json
setup.local.html
```

و `tools/verify.mjs` در CI، الگوهای `github_pat_…` و `ghp_…` را در تمام فایل‌های متنی
جستجو می‌کند تا اشتباه انسانی قبل از انتشار گرفته شود.

## صفحه راه‌اندازی عمومی نیست

`setup/index.html` تنها صفحه‌ای است که می‌تواند `data/vault.json` را بنویسد (با توکنی که
شما وارد می‌کنید). اگر این صفحه روی GitHub Pages منتشر شود، هر بازدیدکننده‌ای می‌تواند
vault دلخواه خودش را جایگزین کند و کنترل مدیریت سایت را بگیرد.

به همین دلیل گردش‌کار `.github/workflows/pages.yml` این پوشه را **کپی نمی‌کند** و
`tools/verify.mjs` در CI بررسی می‌کند که دوباره به خروجی اضافه نشود. راه‌اندازی فقط
روی دستگاه خودتان انجام می‌شود:

```bash
npm start        # سپس http://localhost:8080/setup/
```

چون `/setup/` هیچ لینکی از سایت عمومی ندارد، عملاً «ابزار محلی» است نه صفحه‌ای از سایت.

## چرا این روش امن است؟

### ۱. رمز، توکن نیست

رمز شما فقط یک «کلید باز کردن قفل» است. اگر کسی رمز شما را ببیند، در واقع به توکن دسترسی
پیدا **می‌کند** (چون می‌تواند vault را رمزگشایی کند) — اما خود رمز هیچ متن ساده‌ای از
توکن نیست که در گیت‌هاب یا لاگ‌ها لو برود.

### ۲. توکن محدود است، نه عمومی

توکن پیشنهادی *Fine-grained* فقط به **یک مخزن** و فقط به **Contents: Read and write**
دسترسی دارد. حتی اگر لو برود، نمی‌تواند به مخازن دیگر یا تنظیمات حساب دسترسی داشته باشد.

### ۳. رمزگذاری شناخته‌شده و استاندارد

| مؤلفه | انتخاب | دلیل |
| --- | --- | --- |
| KDF | PBKDF2-SHA256، ۳۰۰٬۰۰۰ دور | استاندارد وب، در همه مرورگرها بدون کتابخانه |
| Salt | ۱۶ بایت تصادفی، یکتا برای هر vault | جلوگیری از rainbow table |
| رمزنگاری | AES-256-GCM | رمزنگاری احراز‌شده؛ هر تغییر در ciphertext باعث خطا می‌شود |
| IV | ۱۲ بایت تصادفی، یکتا برای هر رمزگذاری | الزام GCM |
| محل کلید | حافظه مرورگر (غیرقابل استخراج) | کلید هرگز روی دیسک نوشته نمی‌شود |

### ۴. هیچ سروری، هیچ لاگی

رمزنگاری/رمزگشایی در `crypto.subtle` مرورگر انجام می‌شود. هیچ درخواستی حاوی رمز به
هیچ سروری فرستاده نمی‌شود. تنها درخواست‌های شبکه، دریافت `store.json` و درخواست‌های
`api.github.com` با `Authorization: Bearer` هستند.

### ۵. محافظت در برابر حدس زدن رمز

در ورود، ۵ تلاش ناموفق یک تأخیر تدریجی (۳۰ ثانیه تا ۵ دقیقه) فعال می‌کند. این محافظت
سمت کلاینت است و با پاک کردن `localStorage` دور می‌خورد، اما در عمل کار حمله خودکار از
مرورگر را بسیار کند می‌کند.

> واقعیت: هر کسی که به `vault.json` دسترسی دارد، می‌تواند **آفلاین** و بدون محدودیت
> تلاش کند. تنها سد واقعی، **قدرت رمز** است. یک رمز ۴ کلمه‌ای طولانی (مثل
> `کافه-۱۲۴-آفتاب-شمال`) با ۳۰۰ هزار دور PBKDF2 عملاً شکستن‌ناپذیر است؛
> `12345678` در چند ثانیه شکسته می‌شود.

### ۶. CSP سخت‌گیرانه

هر دو صفحه یک `Content-Security-Policy` متا دارند:

```
default-src 'self';
script-src 'self';            ← هیچ اسکریپت درون‌خطی یا خارجی
style-src 'self' 'unsafe-inline';
connect-src 'self' https://api.github.com https://raw.githubusercontent.com;
img-src 'self' data: https:;
object-src 'none'; base-uri 'self'; form-action 'self';
```

نتیجه: حتی اگر کسی محتوا را در `store.json` تغییر دهد (که با توکن شما امکان‌پذیر است)،
نمی‌تواند اسکریپت تزریق کند، چون نام/توضیح‌ها همیشه با `textContent`/escape رندر می‌شوند.

## چه چیزی محافظت **نمی‌شود**

- **قیمت‌ها و موجودی** عمومی هستند؛ این هدف پروژه است.
- **نام فروشگاه، تلفن، آدرس** عمومی هستند.
- **یادآور رمز** (اگر پر شود) عمومی است. هرگز خود رمز را در آن ننویسید.
- **تاریخچه تغییرات** (چه کسی، چه‌وقت) عمومی است.

---

## چک‌لیست امنیتی پیشنهادی

- [ ] رمز حداقل ۴ کلمه‌ی بی‌ربط یا ۱۶ کاراکتر تصادفی باشد.
- [ ] توکن Fine-grained مخصوص همان مخزن، با انقضا.
- [ ] توکن را جای دیگری ذخیره نکنید (نه Notion، نه چت، نه فایل متنی در مخزن).
- [ ] هر ۹۰ روز توکن را Revoke و از «رمز و توکن» جایگزین کنید.
- [ ] اگر دستگاه مشترک دارید، بعد از هر بار کار، دکمه **قفل** را بزنید.
- [ ] `node tools/verify.mjs` را قبل از هر push اجرا کنید.
- [ ] اگر رمز لو رفت: صفحه راه‌اندازی → توکن جدید → رمز جدید.

## سناریوهای حمله و پاسخ

| سناریو | نتیجه |
| --- | --- |
| مهاجم مخزن را fork می‌کند | فقط `store.json` عمومی و `vault.json` رمزگذاری‌شده را می‌گیرد. بدون رمز، بی‌فایده. |
| مهاجم رمز ضعیف را با brute-force می‌شکند | ممکن است؛ اگر رمز ضعیف باشد، دیگران می‌توانند با شما ادیت کنند. **از رمز قوی استفاده کنید.** |
| مهاجم در `store.json` مالوِر می‌گذارد | نیاز به توکن دارد؛ اگر داشت، CSP و escape مانع اجرای اسکریپت می‌شوند. |
| توکن لو می‌رود | فقط روی یک مخزن اثر دارد؛ Revoke کنید و توکن تازه بسازید. |
| مدیر روی دستگاه عمومی وارد می‌شود و نمی‌بندد | توکن در حافظه تب می‌ماند تا بسته شود. دکمه **قفل** آن را پاک می‌کند. |
| MITM روی شبکه عمومی | GitHub Pages و api.github.com فقط HTTPS هستند؛ Web Crypto روی HTTP غیرفعال است. |
| XSS از طریق ورودی مدیر | همه خروجی‌ها escape می‌شوند و CSP اسکریپت درون‌خطی را ممنوع می‌کند. |
